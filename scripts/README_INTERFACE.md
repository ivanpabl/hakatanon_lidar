# Контракт: алгоритм обнаружения ↔ остальная команда

Файл `detector_interface.py` — единственное, что нужно знать остальной команде
про алгоритмическую часть. Никаких ROS2/Docker-зависимостей внутри — только numpy.

## Как использовать

```python
from detector_interface import ObstacleDetector, parse_pointcloud2

det = ObstacleDetector()
frame_i = 0

def on_pointcloud(msg):  # msg: sensor_msgs.msg.PointCloud2 (настоящий, из rclpy)
    global frame_i
    x, y, z = parse_pointcloud2(msg.data, msg.point_step)
    result = det.detect(x, y, z, refit_path=(frame_i % 10 == 0))
    publish(result)
    frame_i += 1
```

`parse_pointcloud2` работает с любым объектом, у которого есть `.data` (байты)
и `.point_step` (int) — не важно, настоящее это сообщение rclpy или
десериализованное через `rosbags`.

## Система координат (важно, не очевидно из ТЗ)

Установлено эмпирически по реальным данным, а не выбрано нами:
- `x` — вбок (лево/право)
- **вперёд = `-y`** (не `+y`!)
- `z` — вверх

Если в реальном ROS2-топике окажется другая конвенция (другой TF-фрейм) —
здесь придётся поправить знак, в остальном коде ничего менять не нужно.

## Формат результата `detect()`

```python
{
    'obstacle': bool,          # есть ли препятствие в кадре
    'distance_m': float|None,  # дистанция до ближайшей точки препятствия
    'n_points': int,           # сколько точек попало в зону проверки (для отладки)
    'path_available': bool,    # найден ли путь по рельсам (или используется fallback "прямая линия")
    'gauge_m': float|None,     # найденная колея, для диагностики (эталон 1.52м)
}
```

## Тайминги (замерено на реальных бегах, см. `benchmark_latency.py`)

| Операция | Время | Частота |
|---|---|---|
| `parse_pointcloud2` | 3-14 мс | — |
| `check_frame` (быстрая проверка) | <2 мс | 140-260 FPS |
| `update_path` / `refit_path=True` (геометрия пути) | ~90-98 мс | ~10-11 Гц |

**Важно:** `refit_path=True` передавать не на каждом кадре — родная частота
лидара ~9.86 Гц, а пересчёт пути занимает почти столько же времени, сколько
интервал между кадрами. Звать его раз в N кадров (например, раз в секунду)
достаточно — путь физически не меняется так быстро, как двигается лидар.
Проверку препятствия (`check_frame`, входит в `detect()` всегда) — звать
каждый кадр, она укладывается с большим запасом.

## Что уже честно проверено, а что нет

- Проверено на **синтетике** (симулятор `lidar_sim.py`, реальная 128-канальная
  таблица сенсора): обнаружение крупного объекта (0.7м) на 20-300м без ложных
  тревог на пустом тоннеле.
- Проверено на **реальных данных**: поиск пути по рельсам работает на 4 из 6
  бегов (колея 1.5-1.65м). На 2 бегах — не работает (см. `diagnose_obstacle_lidar.py`
  для разбора причин: один случай — баг подбора пары, другой — другой лидар).
- **Не проверено**: полный `detect()` целиком на реальном bag с настоящим
  препятствием (`doubleT_obstacle`) — мы не смогли надёжно найти в нём само
  препятствие, чтобы сравнить с ground truth (см. `find_real_obstacle.py`,
  `scan_doubleT_obstacle_frames.py`).
- Параметры `near_cutoff`, `half_width`, `air_gap_above_floor`, `air_height` в
  `ObstacleDetector.__init__` — калибровка на синтетике, не финальная. Могут
  требовать донастройки на реальных данных без изменения самого интерфейса.

## Что можно делать параллельно, не дожидаясь финальной версии алгоритма

Всё это не зависит от внутренностей `detector_interface.py`, только от
сигнатуры выше:

1. **ROS2-нода + Docker** — подписка на топик лидара, вызов `detect()`,
   публикация результата. `docker build → docker run → ros2 bag play` можно
   довести до рабочего состояния прямо сейчас, вызывая `detect()` даже с
   текущими (не финальными) параметрами — сигнатура не изменится.
2. **README, архитектура, демо/RViz, видео** — не зависят от качества алгоритма.
3. **Автоопределение топика лидара** (вместо хардкода имени топика) — отдельная
   задача, не связанная с этим файлом.
