# Роадмап «на максимум»: путь к безоговорочной победе

Идея на будущее (не для сдачи 29.09). Фиксирует стратегию доведения решения до
уровня, при котором оно обгоняет `tunnelguard-lct2026-main` не по одной метрике,
а по совокупности того, что судит жюри. Основано на анализе в
[COMPETITOR_TUNNELGUARD.md](COMPETITOR_TUNNELGUARD.md).

## Где мы проигрываем сейчас (три разрыва)

1. **Ложные СТОП.** 3,0 % на полной записи `new_data` против их ~0,32 % на
   запечатанном блоке. Главный критерий ТЗ («надёжно видеть препятствие без
   ложных тревог») — доминирует над остальными.
2. **Методика.** У них LORO, запечатанный блок, 3 зерна, абляция каждого
   компонента, self-labeling проездом насквозь, задокументированные неудачи.
   У нас — нет. Жюри читает это как инженерную зрелость.
3. **Подача.** Живой 3D, видео, презентация. При близких результатах решает питч.

Где мы уже лучше и что НЕ отдаём: **дальность** (159 / 187 м против их 142–150 м),
задержка, устойчивый приём больших кадров, объяснимость без ML.

## Целевое состояние

Не «сократить отрыв», а доминировать на каждой оси и добавить то, чего нет ни у
кого. Забрать их метрику (ложные < 0,5–1 %), НЕ отдав свою (дальность 180+ м),
плюс два дифференциатора, которых ML-команды дать не могут:

- **Провенанс каждого СТОП** — система называет физическую причину, проверяемую
  человеком («объект в габарите на 47 м, 1,2 м, не поверхность: 8 лучей, стена сбоку»).
- **Safety case** — ODD + анализ отказов, читается как документ внедрения.

## Фаза A. Ложные СТОП (ядро оценки)

Источники ложных и удары по каждому:

### A1. Мультиголос правдоподобия (дёшево, уже окупаемо)
Признаки `side_n`, `rings`/`ext_beams`, `wall_left/right_n` в
`plausibility.object_features` **уже считаются**, но в `decision.object_level`
используется только `behind_n`. Свести их в комбинацию голосов (СТОП→ВНИМАНИЕ при
2+ признаках «поверхность»), не отдельными порогами. Диагностика разделимости
TP/FP на `runs/cand_fo.jsonl`, как делали для `behind_n`. Риск для дальности
минимальный. **Первый шаг — с него начинать.**

### A2. σ(x)-габарит (главный рычаг, крупнее)
Оценить σ оси как функцию дальности (разброс `cl(fwd)` от параболы + остаток
трассировки рельсов) + σ полотна + σ калибровки → единый бюджет геометрической
ошибки. Тревога только внутри `half_width − k·σ(x)`: вблизи σ мал (зона полная,
безопасность и близкие объекты сохранены), вдали жмётся (пол на подъёме, стена в
кривой выпадают). Обобщает костыли `far_half_width`/`far_top`/`plausible_*` в один
защитимый принцип.

### A3. Калиброванные вероятности вместо порогов
Все признаки → вероятности «поверхность vs предмет», байесовское объединение с
явной ценой ошибки (пропуск дороже вблизи, ложная — наоборот вдали). A1 — заготовка
под это.

### A4. Временная фильтрация в дальней зоне
Далеко поднять `confirm_hits`/`evidence_threshold`, вблизи оставить. Проверить
`ego_min_travel`. Гасит одиночные вспышки, не трогая близкие реальные объекты.

**НЕ трогать:** ближние остатки пола оставляем как СТОП — асимметрия безопасности
(пропуск близкого реального объекта хуже лишнего торможения). σ-сжатие там не
сработает (σ мал) — и хорошо.

## Фаза B. Методика (дёшево, высокий вес у жюри)

Кода почти не требует, идёт параллельно с A.

- **B1. Абляция.** `research/compare.sh` с поочерёдным выключением `ego_check`,
  `plausibility`, `far_axis`, `edge_lines` (тумблеры уже в конфиге) → таблица
  «что даёт каждый блок».
- **B2. Запечатанный блок + устойчивость.** Отложить запись, не трогать при тюнинге,
  метрика на ней в конце. Несколько зёрен. Задокументировать отвергнутые гипотезы
  (shell-veto уже отвергнут по данным — готовый пункт).
- **B3. LORO** по всем записям — становится осмысленным только при разнообразных данных.
- **B4. PR-кривые и калибровка по полосам дальности** (0–30 / 30–100 / 100–200 м).

## Фаза C. Safety case (главный дифференциатор)

Ни у нас, ни у них этого нет. Отраслевое жюри оценит выше метрики.

- **ODD** — в каких тоннелях/скоростях/условиях система заявлена рабочей, с границами.
- **Анализ отказов** — потеря лидара, забрызганная оптика, пыль, вода, встречный
  поезд, засветка. Для каждого — заявленное fail-safe поведение (→ СТОП, не молчание).
- **Провенанс СТОП** — физическая причина каждого решения, доведённая до
  продуктового уровня.
- Обоснование дальности: скоростной профиль / тормозной путь → 180 м достаточно.

## Фаза D. Подача

Живой 3D-просмотр прогона с маркерами и подписью причины решения; видео сложных
сценариев; одностраничник (числа, схема пайплайна, таблица абляции, ODD).

## Опция: ML-верификатор (осторожно)

Только как **верификатор-резидуал**: может понизить уверенность или подтвердить,
но **никогда не поднять СТОП сам**. Обучен на self-labeling. Полностью абляcируемый.
Так добираем точность без риска переобучения, который жюри штрафует. **НЕ** делать
ML основным решателем — сожжёт наше преимущество в объяснимости и дальности.

## Данные и железо

### Данные — главный ограничитель (не код, не железо)
- **Публичных датасетов под наш кейс (лидар + препятствия в метро-тоннеле) нет.**
- **OSDaR23** — лучший заменитель: наземная ж/д, Гамбург, 1534 кадра, 3D-кубоиды +
  разметка путей + семантика, для беспилотных поездов. Валидирует трассировку,
  габарит и **перенос на чужой сенсор** (Velodyne HDL-64 vs наш Pandar128).
- **SemanticRail3D / WHU-Railway3D / Rail3D** — сегментация коридора, без объектов.
- Тоннели метро в открытых наборах есть только для **инспекции** (деформация, течи) —
  препятствий нет, для нас почти бесполезны.
- **Граница:** публичные данные закрывают обобщение и трассировку, но НЕ главную
  метрику (ложные в замкнутом тоннеле) и НЕ safety-сценарии — их добывать самим
  (записи организаторов, свои записи, синтез).

### Что делаем с датасетом
Ядро геометрическое — **обучать нечего**. Датасет = полигон проверки обобщения:
выбрать подмножество → адаптер их формата (OpenLABEL, оси, поля PointCloud2) в наш
вход → **прогнать наш алгоритм** → сравнить с их 3D-разметкой. Обучение — только под
опциональный ML-верификатор.

### Железо
- **GPU нам почти ничего не даёт** — ядро это numpy, упирается в CPU и диск. GPU
  нужен только под обучение ML-верификатора.
- **Приоритет: SSD/NVMe + много физических ядер CPU.**
- Прикидка места: OSDaR23 полный ~80–120 ГБ (лидар-подмножество ~15–25 ГБ), запас
  ~250–300 ГБ.

### Схема прогона с HDD-архивом (staging)
```
HDD (архив)
   │  prefetch: копируем блок N+1, пока считается блок N
   ▼
SSD (буфер, 1–2 блока)  ──▶  Pool(6, по числу физ. ядер) по bag'ам  ──▶  результаты на HDD
   │
   └─ очистка блока N после сохранения его результатов
```
Правки к наивной схеме: **prefetch следующего блока во время счёта**;
**workers = число физических ядер (6), а не потоков (12)** — счёт CPU-bound, SMT даёт
10–20 %. Параллелизм у нас **по bag'ам** (`Pool(min(len(bags), workers))`) — в блоке
должно быть ≥ ядер записей, иначе простой. Результаты писать НЕ в очищаемый буфер.

### Время (прикидка, ~1–2 с/кадр на ядро)
- Один bag (`new_data`): ~15 мин, 1 ядро.
- LORO 8–10 записей: ~20–40 мин на 16 ядрах + **NVMe**; на HDD — часы (контокуренция
  за головку при параллельном чтении → нужен staging выше).
- Обучение ML-верификатора: часы–день, разово, GPU.

## Что даёт большой прогон

Сам по себе алгоритм НЕ улучшает (обучать нечего). Даёт:
1. **Статистику вместо анекдота** — ложные как процент с доверительным интервалом,
   а не «4 на одном bag'е». Прямая атака на их 0,32 %.
2. **Доказательство обобщения** — работает на невиданных тоннелях/сенсорах. Закрывает
   их методический отрыв.
3. **Вскрывает источники ложных**, невидимые на 1–2 записях, — топливо для итераций A.
4. **Защиту от обвинения в переобучении** — #1 подозрение технического жюри.

Граница: публичные наборы (наземная ж/д) НЕ измеряют ложные в тоннеле — её мерить на
данных организаторов.

## Ожидаемый результат (честный прогноз)

| | Сейчас | После плана | Риск |
|---|---|---|---|
| Ложные СТОП (полная запись) | 3,0 % | 0,5–1,5 % | σ-габарит может не дать столько |
| Ложные на bag организаторов | 4 | 1–2 | — |
| Дальность (человек / куб) | 159 / 122 м | сохранить | σ-сжатие может чуть отъесть |
| Реальные объекты на bag | 5/7 | 5/7–6/7 | — |

- **Паритет по ложным вероятен, разгром — нет.** До 0,32 % дотянуться можно, но это
  оптимистичный сценарий, не базовый.
- **Обгоняем не метрикой, а совокупностью:** при сравнимой надёжности мы объяснимы,
  видим дальше, приносим safety case.
- **Полный план + разнообразные данные** (недели): вероятно обгоняем.
  **Только ядро без данных:** паритет, но не обгон (LORO без данных жюри не засчитает).
  **Ничего:** остаёмся вторыми.
- **Главный риск — не техника, а наличие разнообразных записей из тоннелей.**
