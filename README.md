# Обнаружение препятствий в тоннеле метро по 3D-лидару

Система отвечает на вопрос «есть ли на пути поезда что-то, чего там быть не должно, и на каком расстоянии». На вход поступает поток облаков точек 128-канального лидара, на выходе для каждого кадра получается решение «препятствие есть / нет», дистанция до ближайшего препятствия и список найденных объектов.

Подход геометрический, без обучения. Детектор находит рельсы своего пути и строит ось пути. Затем он оценивает высоту полотна по дальности и ищет точки внутри зоны над рельсами вдоль этой оси. Точки собираются в объекты, а тревога поднимается только по объекту, который держится несколько кадров подряд.

## Состав репозитория

```

├── pointcloud.py      разбор PointCloud2, геометрия лучей датчика

tools/                 офлайн-инструменты: оценка, замеры, демонстрация, отрисовка

data/                  записи и картинки разметки (не в git)
runs/                  результаты инструментов (не в git)
```

## Входные данные

Облака приходят как `sensor_msgs/msg/PointCloud2` с полями `x, y, z, intensity` (float32), `ring` (uint16) и `timestamp` (float64), `point_step = 26`. Имя топика в разных записях разное (`/lidar_points`, `/sensing/lidar/hesai128/pointcloud`), поэтому инструменты ищут топик по типу сообщения.

Устройство облака одинаково во всех семи записях:

- облако идёт столбцами по 128 каналов, а пара столбцов `(2k, 2k+1)` — это два отражения (dual return) одного залпа, которые в 97–98% пар совпадают;
- 38–62% точек нулевые `(0, 0, 0)`: луч не вернул отражения;
- азимут пары столбцов равен `A0 − 0,1°·k`, у каждого канала постоянный угол места и постоянный сдвиг азимута (до ±7,8°).

**Система координат:** `x` — вбок, **вперёд — это `−y`**, `z` — вверх. Во всём пакете продольная координата `fwd = −y`, поперечная `lat = x`.

## Обработка кадра

```
PointCloud2
  │
  ▼
parse_pointcloud2 ─── удаление нулевых точек и дублей dual return (облако меньше в 3–5 раз)
  │
  ├──► update_path (раз в N кадров, ~30 мс)
  │      find_floor_bumps ── пики поперечного профиля высоты = кандидаты в головки рельсов
  │      trace_rail_pair ─── затравочная пара рядом с лидаром → прослеживание каждого рельса вперёд
  │      fit_path ────────── ось пути до ~40 м (середина рельсов, полином)
  │      rail_offset ─────── высота головки рельса над дном лотка
  │      extend_path_by_walls  ось дальше рельсов по стенам тоннеля
  │
  └──► check_frame (каждый кадр, ~5 мс)
         estimate_bed_profile ── высота дна лотка по дальности
         зона ────────────────── точки ±1 м от оси, 0,15–2 м над головкой рельса
         cluster_points ──────── точки → объекты
         min_points_at ───────── отсев объектов меньше порога по дальности
         Tracker ─────────────── подтверждение: объект в 3 из 5 последних кадров
         path_margin ─────────── тревога только в пределах известной оси + 10 м
  │
  ▼
результат: obstacle, distance_m, objects, …
```

Пересчёт пути заметно дороже проверки кадра, поэтому его можно делать не на каждом кадре. Детектор держит последний найденный путь до `max_path_age` кадров.

## Модули ядра

| Модуль | Что делает |
|---|---|
| `pointcloud.py` | `parse_pointcloud2`: байты → `x, y, z` без нулей и дублей. `beam_directions`: направление каждого луча, включая лучи без отражения, с точностью лучше 0,001°. `xyz_views`: изменяемые представления полей буфера |
| `geometry/rails.py` | `find_floor_bumps`: пики профиля высоты в срезах по 1 м. `trace_rail_pair`: пара рельсов своего пути. `fit_path`: ось пути |
| `geometry/bed.py` | `estimate_bed_profile`: дно лотка по дальности. `bed_at`: дно лотка на заданной дальности с продолжением за конец профиля. `rail_top_at`: высота головки рельса |
| `geometry/path.py` | `extend_path_by_walls`: продление оси по стенам. `TrackPath`: снимок геометрии пути (ось, полотно, рельсы) для внешних потребителей |
| `detection/zone.py` | зона проверки: прямоугольник по умолчанию, `GAUGE_METRO` как вариант |
| `detection/clustering.py` | `cluster_points`: точки → объекты. `min_points_at`: минимальный размер объекта по дальности |
| `detection/tracking.py` | `Tracker`: сопоставление объектов между кадрами и подтверждение |
| `detection/detector.py` | `ObstacleDetector`: связывает шаги и хранит состояние между кадрами |
| `sim/lidar_sim.py` | синтетический тоннель: цилиндр, пол, рельсы и шар, трассировка лучей по реальной таблице каналов (`ring_table.json`) |
| `sim/shapes.py` | фигуры `Box`, `Cylinder`, `Sphere` с пересечением лучей |
| `sim/inject.py` | `inject`: вставка фигур в реальный кадр по настоящим лучам датчика, с тенью. `on_track`: точка на оси пути |

## Шаги алгоритма и параметры

### Разбор облака
Нулевые точки отбрасываются. Второй столбец пары удаляется, если его точка ближе 1 см (`DUAL_RETURN_DUP_M`) к точке первого столбца.

### Рельсы и ось пути (`geometry/rails.py`)
- Профиль строится в зоне 2–40 м вперёд и ±3,5 м вбок, срезами по 1 м вдоль пути и бинами по 5 см поперёк. В каждом срезе берётся максимум высоты в бине.
- Кандидат в рельс — пик, выступающий над медианой соседних бинов больше чем на 5 см (`PROMINENCE`).
- **Затравка пары** берётся только по пикам ближе 10 м (`SEED_FWD`). Расстояние между рельсами должно быть 1,45–1,75 м (`SEED_GAUGE`), а середина пары — не дальше 0,4 м от лидара (`SEED_MAX_MID`), потому что поезд стоит на своём пути.
- **Прослеживание:** каждый рельс ведётся вперёд срез за срезом. Принимается только пик ближе 12 см (`TRACE_TOL`) к предсказанию по уже найденным точкам. После 8 м без пика (`TRACE_MAX_GAP`) рельс считается потерянным.
- Ось пути — середина полиномов левого и правого рельса (2-й степени на участке длиннее 15 м).

Раньше пики склеивались по боковой координате на всём участке 2–40 м. На кривых и рядом с мусором рельс сцеплялся с соседними линиями, и на станциях и стрелках выбиралась чужая пара. Прослеживание от затравки эту проблему убрало.

### Ось дальше рельсов (`geometry/path.py`)
Рельсы видны до 38–40 м, а стены — до 115–160 м. Где ось известна по рельсам, измеряется расстояние от оси до ближайшей поверхности слева и справа на высоте 0,5–2,5 м над рельсом. Дальше ось ведётся шагами по 4 м так, чтобы это расстояние сохранялось, с допуском 0,3 м. После трёх шагов подряд без стены продление останавливается. Точки ближе 1,1 м к оси в поиск стены не входят, чтобы препятствие на пути не могло «сдвинуть стену».

### Полотно (`geometry/bed.py`)
Полотно вдали лежит на другой высоте, чем вблизи: сказываются уклон пути и наклон лидара. В `doubleT_obstacle` дно лотка на 80 м на 1,3 м ниже, чем на 5 м. Поэтому высота дна лотка между рельсами (полоса ±0,5 м) оценивается в каждом кадре бинами по 4 м как 10-й перцентиль высоты. Бин принимается, только если он продолжает уже принятый профиль с уклоном не больше 6% (прямая Тейла — Сена по последним бинам). Так крупное препятствие, закрывающее полотно, не принимается за «поднявшийся пол» и не прячет само себя.

Головка рельса там, где рельсы найдены, берётся по самим рельсам, а дальше — как дно лотка плюс `rail_offset`. Смещение 0,27–0,56 м в зависимости от типа пути измеряется по участку 5–25 м.

### Зона, объекты, подтверждение (`detection/`)
- **Зона** по умолчанию: ±1,0 м от оси и 0,15–2,0 м над головкой рельса, на дальности 2–250 м.
- **Кластеризация:** разрыв больше 1 м по дальности или больше 0,6 м вбок разделяет объекты. У объекта есть `distance_m` (ближняя точка), `lateral_m`, `height_m` и `n_points`.
- **Порог размера:** объект меньше `max(3, 12000 / d²)` точек помечается `too_small` и не участвует в подтверждении. Это 30 точек на 20 м, 7,5 точки на 40 м и 3 точки начиная с 63 м. Порог откалиброван по вставкам: куб 0,4 м даёт выше 0,15 м примерно `24000 / d²` точек, а порог — половина от этого.
- **Подтверждение:** объект сопоставляется с треком, если он сместился за кадр меньше чем на `2,5 + 0,05·d` м по дальности и 0,8 м вбок. Тревога поднимается, если трек виден в 3 из 5 последних кадров (задержка ~0,3 с при 10 Гц).
- **Ограничение по оси:** объекты дальше известной оси плюс 10 м (`path_margin`) возвращаются в результате, но тревогу не поднимают, потому что коридор там уже догадка.

### Основные параметры `ObstacleDetector`

| Параметр | По умолчанию | Смысл |
|---|---|---|
| `near_cutoff`, `max_range` | 2, 250 м | диапазон дальностей проверки |
| `half_width`, `clearance`, `height` | 1,0; 0,15; 2,0 м | прямоугольная зона |
| `zone` | `None` | своя зона ступенями `(низ, верх, полуширина)`, например `GAUGE_METRO` |
| `min_points_k`, `min_points_floor` | 12000, 3 | порог размера; `0` и `1` выключают его |
| `confirm_hits`, `confirm_window` | 3, 5 | подтверждение по кадрам |
| `path_margin` | 10 м | тревога только до конца известной оси + столько |
| `max_path_age` | 30 кадров | сколько держать путь без пересчёта |
| `default_rail_offset` | 0,5 м | головка рельса над дном лотка, пока не измерена |

## Использование ядра

```python
from tunnel_od import ObstacleDetector, parse_pointcloud2

det = ObstacleDetector()
for i, msg in enumerate(stream):
    x, y, z = parse_pointcloud2(msg.data, msg.point_step, msg.fields)
    result = det.detect(x, y, z, refit_path=(i % 10 == 0))
```

`msg` может быть сообщением из `rosbags` или `sensor_msgs/msg/PointCloud2` из `rclpy`: нужны только `data`, `point_step` и `fields`.

Результат `detect()`:

| Поле | Значение |
|---|---|
| `obstacle` | есть ли подтверждённое препятствие в пределах известной оси |
| `distance_m` | дистанция до ближайшего такого препятствия или `None` |
| `objects` | все объекты кадра: `distance_m`, `lateral_m`, `height_m`, `n_points`, `too_small`, `confirmed`, `beyond_path` |
| `n_points` | точек в зоне |
| `path_available`, `path_age_frames`, `path_range_m` | найден ли путь, давно ли пересчитан, до какой дальности известна ось |
| `gauge_m` | найденная колея (эталон 1,52 м), для диагностики |
| `stamp` | переданная в `detect()` метка времени |

`det.track_path()` возвращает `TrackPath` — снимок оси и высоты рельса. Его используют вставка синтетических объектов и отрисовка.

## Запуск в Docker

ROS 2 Humble, образ на `ros:humble-ros-base-jammy`. Все зависимости ставятся при `docker build`, при запуске сеть не нужна.

```
Dockerfile                          образ: ядро (pip install ./core) + colcon build ros2_ws
run.sh                              сценарий инженера: build / play / detector / test / shell
config/detector.yaml                параметры узла и ObstacleDetector (монтируется в контейнер)
docker/entrypoint.sh                окружение ROS 2 и выбор DDS (TUNNEL_OD_DDS)
docker/play.sh                      внутри контейнера: узел + ros2 bag play + итог
docker/fastdds_shm.xml              FastDDS: shared memory с сегментом 256 МБ (по умолчанию)
docker/cyclone_big.xml              CycloneDDS с большими буферами (запасной вариант)
ros2_ws/src/tunnel_od_detector/     ROS 2-пакет (ament_python): узел, launch, RViz-конфиг
```

### Сборка и прогон записи

```bash
./run.sh build                                   # docker build -t tunnel-od .
./run.sh play /путь/к/записи                     # каталог с metadata.yaml и .db3
./run.sh play /путь/к/записи 0.5                 # rate проигрывания
./run.sh play /путь/к/записи 1.0 --start-offset 5    # дальше -- аргументы ros2 bag play
```

`play` запускает в одном контейнере узел детектора и `ros2 bag play`. Запись монтируется только на чтение. Когда запись кончается, узел печатает итог и останавливается. Результат пишется в `runs/docker/` (переменная `OUT_DIR`):

- `<запись>_result.jsonl`: JSON-результат каждого обработанного кадра, то же, что уходит в `/tunnel_od/result`;
- `<запись>_stats.json`: итог прогона: принято и обработано кадров, отброшено, задержка p50/p95, число кадров с тревогой.

Только узел, без плеера: для своего плеера, драйвера лидара или другой машины.

```bash
./run.sh detector                                # топик ищется автоматически
./run.sh detector topic:=/my/points              # аргументы ros2 launch
# плеер в другом контейнере на том же хосте -- тоже с --network host --ipc host:
docker run --rm --network host --ipc host -v /путь/к/записи:/bag:ro tunnel-od \
    ros2 bag play /bag --read-ahead-queue-size 20 --delay 2
```

Флаги плеера объяснены в разделе «DDS и большие кадры». Без `--start-paused` на старте теряется несколько кадров.

`./run.sh test` запускает pytest узла внутри образа, `./run.sh shell` открывает bash с настроенным окружением.

### Узел `tunnel_od_detector`

Узел подписывается на `sensor_msgs/msg/PointCloud2`. Топик задаётся параметром `topic`; если он пустой, узел берёт первый появившийся топик этого типа (`/lidar_points`, `/sensing/lidar/hesai128/pointcloud`). QoS подписки — `RELIABLE`, как у `ros2 bag play`.

| Топик | Тип | Что внутри |
|---|---|---|
| `/tunnel_od/result` | `std_msgs/String` | JSON на каждый обработанный кадр |
| `/tunnel_od/markers` | `visualization_msgs/MarkerArray` | ось пути, коридор, объекты, текст с решением |

Поля JSON: всё, что вернул `ObstacleDetector.detect()`, плюс служебные поля узла. Новые поля ядра, например `clear_to_m`, попадают в JSON без правки узла. Значения numpy переводятся в числа, NaN и inf — в `null`.

| Поле | Значение |
|---|---|
| `obstacle`, `distance_m` | есть ли подтверждённое препятствие и дистанция до ближайшего, м (`null` — нет) |
| `objects` | все объекты кадра: `distance_m`, `lateral_m`, `height_m`, `n_points`, `confirmed`, `too_small`, `beyond_path`, … |
| `path_available`, `path_range_m`, `path_age_frames` | найден ли путь, до какой дальности известна ось, возраст пути в кадрах |
| `stamp`, `frame_id`, `topic` | `header.stamp` облака (с), система координат, топик |
| `frame` | номер обработанного кадра |
| `latency_ms` | от приёма сообщения узлом до публикации результата |
| `parse_ms`, `detect_ms`, `queue_ms` | разбор облака, детектор, ожидание в очереди узла |
| `refit_mode`, `refit_path`, `path_fit_ms` | как пересчитывается путь, обновился ли он перед кадром, время пересчёта |
| `dropped_total` | сколько кадров отброшено к этому моменту (пришёл более новый) |

Читать результат:

```bash
./run.sh shell
ros2 topic echo /tunnel_od/result --field data         # поток JSON
# или по файлу прогона:
jq -c 'select(.obstacle) | {frame, distance_m}' runs/docker/doubleT_obstacle_result.jsonl
```

В лог узел пишет строку `ТРЕВОГА …` на каждый кадр с тревогой. Раз в `stats_period_s` он выводит сводку: кадров в секунду, задержку p50/p95, сколько кадров принято, обработано и отброшено, сколько пропусков по `header.stamp`. При остановке выводится строка `ИТОГ {...}`.

**Очередь.** Колбэк подписки кладёт кадр в слот на один кадр, обработка идёт в отдельном потоке. Если детектор не успел, старый кадр заменяется новым и учитывается в `dropped_stale`. Так задержка не копится.

**Пересчёт пути.** `update_path` стоит около 80 мс, а разбор и проверка кадра вместе — 20–45 мс. При пересчёте на каждом кадре в 100 мс не уложиться. Поэтому по умолчанию (`refit_mode: async`) путь считается в отдельном процессе по самому свежему кадру и подставляется в детектор перед следующим кадром. Путь отстаёт на 1–2 кадра и совпадает побитно с синхронным `update_path`. Режим `refit_mode: sync` работает как в ядре: `detect(refit_path=(i % refit_every == 0))`.

### Параметры

Все параметры лежат в `config/detector.yaml`. `run.sh` монтирует `config/` в контейнер, поэтому пересобирать образ после правки не нужно. Другой каталог задаётся через `CONFIG_DIR=…`, другой файл — через `./run.sh detector config:=/путь/в/контейнере.yaml`.

- Всё под `detector:` передаётся в `ObstacleDetector(**kwargs)` как есть. Новый аргумент ядра достаточно дописать в YAML. Ключ, которого нет у текущей версии ядра, узел пропускает с предупреждением.
- Для `zone` можно указать имя константы ядра (`GAUGE_METRO`) или плоский список троек `[низ, верх, полуширина, …]`.
- `detector_json` — JSON-строка, которая перекрывает `detector.*`. Она нужна для того, что ROS-параметром не задать: `null`, вложенных списков.
- Параметры узла: `topic`, `refit_mode`, `refit_every`, `qos_reliability`, `qos_depth`, `publish_markers`, `markers_every`, `marker_max_objects`, `log_alarms`, `stats_period_s`, `result_file`, `stats_file`. Описание каждого — в комментариях YAML.

### Свой bag и свой топик

- Запись ROS 2 bag (sqlite3) подаётся каталогом: `./run.sh play /data/my_bag`. Топик облака найдётся по типу. Если в записи несколько облаков, топик задаётся явно: `TOPIC=/my/points ./run.sh play /data/my_bag`.
- Живой лидар или внешний плеер: `./run.sh detector topic:=/my/points`.
- Облако должно быть в системе координат лидара, как в записях: `x` — вбок, вперёд — `−y`, `z` — вверх. Поля `x, y, z` (float32) берутся по `fields`, `point_step` может быть любым.

### RViz

Графика в образ не входит. Конфиг `ros2_ws/src/tunnel_od_detector/rviz/tunnel_od.rviz` открывается на машине с RViz, в той же сети DDS:

```bash
rviz2 -d ros2_ws/src/tunnel_od_detector/rviz/tunnel_od.rviz                 # frame_id hesai_lidar
rviz2 -d ros2_ws/src/tunnel_od_detector/rviz/tunnel_od.rviz -f lidar_livox  # doubleT_obstacle
```

На экране видны облако (обе версии имени топика), ось пути зелёным, коридор синим и объекты. Красные объекты — тревога, жёлтые — не подтверждены, серые — мелкие или за концом оси. Сверху выводится текст с решением и дистанцией.

### DDS и большие кадры

Кадр весит 8 МБ, а в `doubleT_obstacle` — 23 МБ (полный оборот). Выбрана схема «плеер и узел в одном контейнере + FastDDS с транспортом shared memory». `docker/fastdds_shm.xml` задаёт сегмент 256 МБ, `run.sh` добавляет `--shm-size=2g`. Кадр целиком копируется через `/dev/shm` без фрагментации UDP и не зависит от `net.core.rmem_max`. Между контейнерами схема тоже работает (`--network host --ipc host`, режим `detector`). В e2e узел принял все кадры: 345/345 для 8 МБ и 201/201 для 23 МБ.

CycloneDDS с `docker/cyclone_big.xml` и FastDDS по умолчанию тоже дают 10 Гц, но только с увеличенным `net.core.rmem_max`. Поэтому `run.sh` на всякий случай поднимает его через `--sysctl`. Вариант DDS выбирается переменной `TUNNEL_OD_DDS=fastdds_shm|cyclone|default`. Проверка подписчиком без обработки: 8 МБ — 10 Гц у всех трёх вариантов; 23 МБ — FastDDS SHM 201/201, по умолчанию 190/201, Cyclone 189/201.

У `ros2 bag play` в Humble есть две ловушки, и `play.sh` обходит обе.

1. Перед стартом плеер заполняет очередь чтения, по умолчанию 1000 сообщений. Для этих записей это вся запись: 3–5 ГБ в памяти, около 20 с тишины, затем пачка кадров, а на 23-МБ записи — зависание. Именно это раньше выглядело как «DDS не доставляет большие кадры». Лечится флагом `--read-ahead-queue-size 20`.
2. Часы плеера запускаются раньше, чем очередь готова, поэтому первые 1–2 с записи уходят пачкой. Узел берёт из пачки последний кадр, остальные отбрасывает: 8–16 кадров на старте. Поэтому плеер стартует с `--start-paused`, а через `PLAY_DELAY` секунд (по умолчанию 3) `play.sh` снимает его с паузы сервисом `/rosbag2_player/resume`. За это время DDS успевает связать плеер с узлом (QoS `VOLATILE`: кадры до связи теряются), а плеер заполняет очередь.

Внешний плеер нужно запускать так же: `--read-ahead-queue-size 20 --start-paused`, затем `ros2 service call /rosbag2_player/resume rosbag2_interfaces/srv/Resume`.

**Скорость чтения записи.** Для 23 МБ × 10 Гц нужно 240 МБ/с. На машине разработки (macOS, Docker в VM) это предел диска. Если в логе плеера появляется «Message queue starved», кадры идут реже 10 Гц; это ограничение стенда, а не узла. В таком случае можно проигрывать медленнее: `./run.sh play <запись> 0.5`.

### Замеры e2e

`./run.sh play <запись> [rate]`, 26.09, Intel i5-1038NG7 (4 ядра / 8 потоков), Docker в VM OrbStack. Параллельно шли чужие расчёты, средняя загрузка 6–11. Задержка — от приёма сообщения узлом до публикации `/tunnel_od/result`. Путь пересчитывается асинхронно (`refit_mode: async`).

| Запись | Кадр | Кадров в bag | Принято | Обработано | Задержка p50 / p95 | Кадров с тревогой (ближайшая) |
|---|---|---|---|---|---|---|
| `doubleT_platform` | 8 МБ | 345 | 345 | 340 (98,6 %) | 23 / 35 мс | 235 (41,7 м) |
| `roundT_doubleT` | 8 МБ | 252 | 252 | 251 (99,6 %) | 21 / 28 мс | 54 (47,2 м) |
| `squareT_platform_squareT_switch` | 8 МБ | 877 | 877 | 874 (99,7 %) | 23 / 36 мс | 24 (39,4 м) |

| `doubleT_obstacle`, rate 0,5 | 23 МБ | 201 | 201 | 201 (100 %) | 38 / 49 мс | 85 (55,5 м) |

- Кадр 8 МБ обрабатывается за 20–27 мс: разбор 7–10 мс, детектор 15–20 мс. Кадр 23 МБ — за 40 мс: разбор 20 мс, детектор 20 мс. Фоновый пересчёт пути занимает 100–120 мс и обновляет путь раз в 1–3 кадра.
- `doubleT_obstacle` при rate 1,0: все 20 отброшенных кадров приходятся на первые 2 с. Первый кадр 23 МБ обрабатывается около 0,5 с, потом был всплеск загрузки машины. Дальше 10 Гц без потерь, p50 30–50 мс.
- `doubleT_obstacle`: тревога держится в кадрах ~24–64 на 55,5–56,4 м. Объект высотой 0,9–1,5 м смещается вбок с 0,2 до 0,9 м от оси.
- Тревоги в записях без препятствий — ложные срабатывания текущей версии ядра, а не обёртки (см. «Известные ограничения»).

## Инструменты (`tools/`)

Работают по записям в `data/` (`tools/bags.py`) и пишут результаты в `runs/`. Каждый процесс использует numpy в один поток, число процессов задаётся `--workers` (по умолчанию 2).

| Команда | Что делает |
|---|---|
| `python tools/alarms.py --tag v2` | детектор по всем кадрам записей без вставок: сколько тревог. Результат по каждому кадру в `runs/alarms_<tag>.csv`, чтобы сравнивать версии |
| `python tools/eval_injection.py [--quick]` | синтетические объекты (8 фигур, 10 дальностей, на оси, на краю и вне зоны) в окнах реальных записей: доля найденных, точки на объекте, ошибка дистанции, задержка |
| `python tools/benchmark.py` | время разбора, пересчёта пути и проверки кадра |
| `python tools/inject_demo.py --bag … --fwd 56` | вставка объекта в несколько кадров подряд с картинками до и после |

У `alarms.py` и `eval_injection.py` есть флаги `--corridor rect|gauge` и `--minpts on|off` для сравнения вариантов зоны и порога.

Вставка «снимает» объект лучами настоящего датчика, поэтому плотность точек и тень получаются как у реального объекта. Эталоном служат параметры вставки. Объект ставится на ось, найденную детектором, низом на головку рельса.

## Известные ограничения

Цифры получены на записях из `data/` инструментами `tools/`.

- **Дальность.** Объекты от 0,4 м находятся в 83% случаев до 40 м, в 73% на 40–80 м и в 43% на 80–130 м. Дальше 130 м объект почти всегда за концом известной оси, и тревога не поднимается.
- **Ложные тревоги.** Тревога есть в 14% кадров записей, которые считаются пустыми. Большинство таких тревог — крупные объекты на 40–80 м у края зоны, где ось продлена по стенам.
- **Низкие предметы** (ниже 0,15 м над рельсом) не видны по построению зоны.
- **Объекты у края габарита** (1,0–1,35 м от оси) прямоугольная зона не видит. `GAUGE_METRO` их находит, но поднимает тревоги в 86% кадров: захватывает свод и стены.
- **Порог размера** отсекает объекты около 0,2 м. В `doubleT_obstacle` он теряет реальный объект на 56 м после 6-й секунды записи.
- **Эталона на реальных данных нет:** ручная разметка подготовлена, но не проведена. Синтетическая оценка оптимистична: объект стоит на головке рельса, а не на дне лотка, и неподвижен относительно поезда.
