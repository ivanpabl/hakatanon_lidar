# Обнаружение препятствий в тоннеле метро по 3D-лидару

Система отвечает на вопрос «есть ли на пути поезда что-то, чего там быть не должно, и на каком расстоянии». На вход поступает поток облаков точек 128-канального лидара, на выходе для каждого кадра получается решение — СТОП / ВНИМАНИЕ / СВОБОДНО или «путь не определён», — дистанция до ближайшего препятствия, докуда путь проверен свободным, и список найденных объектов.

Подход геометрический, без обучения. Детектор находит рельсы своего пути и строит ось пути: вблизи по рельсам, дальше по стенам тоннеля, до 150–200 м. Затем он оценивает высоту полотна по дальности и ищет точки внутри зоны над рельсами вдоль этой оси. Точки собираются в объекты. Продольные конструкции у края коридора (кабели, контактный рельс, стена в кривой) отсеиваются. Свидетельство по каждому объекту копится по кадрам с учётом движения поезда, и тревога поднимается, когда его набралось достаточно. Поэтому дальний объект из 1–2 точек на кадр подтверждается за несколько кадров.

Главные цифры (подробно — «Качество» ниже):
- на бэге организаторов с 10 объектами — СТОП на 5 из 7 объектов в габарите (98, 44, 48, 186 и 100 м), ни одного СТОП на трёх объектах вне габарита; ложных СТОП-кадров 4 из 1510 (было 19 до фильтра правдоподобности);
- на всей отложенной записи `new_data` (18,8 мин) — 3,0 % кадров СТОП (было 4,4 %: фильтр правдоподобности убрал дальние ложные тревоги, где поверхность скользнула в коридор); почти все эпизоды СТОП доказанно ложные (поезд потом проехал это место);
- человек впервые подтверждается в среднем на 159 м при подъезде со 170 м и на 187 м со 220 м;
- в Docker без сети обработка кадра 8 МБ занимает p95 68 мс при 10 Гц, от публикации кадра до результата — p95 88 мс.

## Быстрый старт

Нужен только Docker. Одна команда собирает образ и прогоняет запись:

```bash
BAG=/путь/к/записи docker compose up --build
```

`BAG` — каталог записи `ros2 bag` (внутри `metadata.yaml` и `*.db3`). Результат появится в `./out`:

```
<имя>_result.jsonl        решение по каждому кадру
<имя>_stats.json          итог по записи
<имя>_stats_preproc.json  C++-приём кадров и проверка входного потока
<имя>_e2e.json            задержка «кадр опубликован -> результат опубликован»
```

Если стенд проверки без интернета, к решению приложен готовый образ под x86-64 — тогда сборка не нужна:

```bash
docker load -i tunnel_od_image.tar.gz
BAG=/путь/к/записи docker compose up
```

Остальные режимы — профили той же команды:

```bash
docker compose --profile test up --build      # gtest канонизации облака + pytest узлов
docker compose --profile live up --build      # только узел: внешний плеер или живой лидар
docker compose --profile metrics up --build   # метрики и демо в ./out (нужен ./data)
```

Все переменные (`NAME`, `RATE`, `TOPIC`, `TUNNEL_OD_DDS`, `LAUNCH_ARGS`, `PROBE`) описаны в шапке
`docker-compose.yml`. Параметры детектора — `config/detector.yaml`, он монтируется в контейнер,
поэтому меняется без пересборки.

## Как это работает

Кратко: разбор облака → рельсы и ось пути (вблизи по рельсам, дальше по стенам, до 150–200 м) →
профиль высоты полотна по дальности → точки в зоне над рельсами → кластеры → отсев продольных
конструкций у края коридора → накопление свидетельства по кадрам с учётом пробега → решение
по кадру. Подробно, с каждым параметром и порогом, — в [docs/ALGORITHM.md](docs/ALGORITHM.md).

### Ложные тревоги

- **Пять пустых записей** из `for_hackathon` (3,8 мин): на них подбирались настройки до появления бэга организаторов.
- **`new_data`** — отложенная запись, при подборе не использовалась. Итог на всей записи: 3,0 % кадров СТОП, 97 эпизодов (310 в час), медиана дистанции 45 м. Фильтр правдоподобности (см. «Шаги алгоритма») убрал дальние ложные СТОП (было 4,4 %, медиана 68 м); оставшиеся — в основном ближняя зона, где над порогом полотна (0,15 м) пробивается его остаточная текстура (см. «Известные ограничения»).
- **Саморазметка проездом** (`tools/selflabel.py`): эпизод СТОП доказанно ложный, если поезд потом проехал это место и не остановился. На `new_data` из 218 эпизодов по трекам доказанно ложные 217, не разрешён 1. Оговорка: пробег по нашей одометрии 9,7 км за 18,8 мин, у другой команды (TunnelGuard) — 13,0 км. Если наша одометрия занижает скорость, проверка «проехал место» слишком строгая, и вывод «ложный» только надёжнее. Но пока расхождение не объяснено, инструмент помечает сводку как ненадёжную.
- **Природа ложных СТОП.** Наклон «дистанция / пробег» у подтверждённых объектов почти везде около −1 (медиана −1,00, 5–95 % — −1,22…−0,78). Значит, ложные СТОП — неподвижные в мире конструкции у края зоны, а не артефакты, едущие с поездом. ЭГО-тест их почти не снимает: на `new_data` он убрал 6 кадров СТОП.
- **`unknown`** (ось не найдена): 0 кадров на всех записях, включая `new_data` и бэг организаторов.
- **`doubleT_obstacle`**: поезд стоит всю запись. На 56 м в кадрах 12–68 стоит человек (узкий столб точек до ~1,5 м над рельсом, 0,7–0,9 м от оси), в остальных кадрах СТОП держат 2–3 низкие точки неподвижного мелкого предмета на −0,77 м. СТОП в 191 кадре из 201.
- **Детерминизм:** два одинаковых прогона по 5 пустым записям дают побитово одинаковый CSV.

### Дальность

`tools/eval_approach.py`: синтетический объект неподвижен в мире, поезд к нему едет (смещение за кадр — по скорости из сцены). Это ровно то, что оценивает ТЗ §8.2. Медиана дальности первого подтверждения по 6 окнам движения (4–15 м/с), исходная версия (`ae38df6`) → итог:

| Объект, старт подъезда | 130 м | 170 м | 220 м |
|---|---|---|---|
| человек стоит | 116 → 125 м | 116 → **159 м** | не найден → **187 м** (50 %) |
| куб 0,4 м | 101 → 121 м | 118 → **152 м** | не найден → 186 м (33 %) |
| человек лежит | 99 → 112 м | 118 → 150 м | не найден → 182 м (33 %) |

Ошибка дистанции при первом подтверждении: медиана 3 см, 95 % — до 1 м (вдали).


## Известные ограничения

- **Выборки маленькие.** Замеры дальности сделаны на 6 окнах движения, ложные тревоги — на 22,6 минутах записей. Разметки реальных препятствий, кроме `doubleT_obstacle`, нет, а вставка синтетики оптимистична: объект ставится на ось, найденную самим детектором, поэтому ошибка оси в оценку дальности не попадает. Её ловят только ложные тревоги.
- **Кривые.** В кривой путь дальше 60–120 м закрыт внутренней стеной: прямая видимость по оси около 2·√(2·R·c), где c ≈ 1,5–2 м — расстояние от оси до стены. Ось там продлевается по внешней стене, но объект на пути физически не виден.
- **Низкие предметы** (ниже 0,15 м над головкой рельса) не видны по построению зоны. В том числе минимальное препятствие из ТЗ, 300×300×100 мм, если оно лежит плашмя: его верх на 0,1 м, ниже зоны. Опустить зону не получается: на пустых записях остаток до фона у полотна больше 8 см в 4–18 % ячеек.
- **Объекты генератора ниже полотна.** На бэге организаторов объекты 3 (низ 0,07 м) и 9 (0,01 м) частично ниже зоны; СТОП они получают за счёт верхней части (3) и того, что вдали плита парит над рельсами из-за уклона (9). Пропущенных из-за этого объектов нет.
- **Ширина зоны 1,0 м, а габарит организаторов — ±1,15 м.** Объекты у края габарита (1,0–1,15 м от оси) получают только ВНИМАНИЕ: на бэге организаторов это объект 4, и объект 6 большую часть времени. Шире сделать нельзя: ошибка нашей оси на 30–60 м достигает ~0,3 м, и зона шире 1,0 м даёт СТОП на объекте 5 за габаритом. Вдали, в дальней зоне, не видны объекты с медианным смещением больше 0,7 м.
- **Высота зоны 2,5 м.** Предметы, свисающие со свода ниже 2,5 м над головкой рельса, видны. Тонкий стержень организаторов с низом на 2,7 м (объект 10) — нет.
- **ЭГО-тест.** Поезд впереди, идущий в ту же сторону с той же скоростью, или человек, уходящий от поезда, держат дистанцию, и получают ВНИМАНИЕ вместо СТОП. Если объект начнёт приближаться, наклон вернётся к −1, и СТОП восстановится.
- **Стекло** лидар не видит: видны только отражения и рамы.
- **Длинные объекты вдоль пути** в дальней зоне (длиннее 5 м, например состав) отсеиваются как конструкции.
- **Кадры 23 МБ** (полный оборот, `doubleT_obstacle`) на macOS в Docker частично теряются из-за скорости диска: обработано 191 из 201 принятого. На кадрах 8 МБ, как на проверке, отброшен 1 кадр из 345.


## Инструменты (`tools/`)

Запускаются профилем `metrics` целиком (`tools/run_all.py`) либо по отдельности внутри того же
образа. Работают по записям в `data/` (`tools/bags.py`), результаты пишут в `out/runs/`.
Каждый процесс считает numpy в один поток, число процессов — `--workers`.

| Команда | Что делает |
|---|---|
| `tools/run_all.py [--quick]` | всё сразу: тесты, метрики качества, проверка входа, `metrics.html` и `demo.html` |
| `tools/alarms.py --tag v2` | детектор по всем кадрам записей без вставок: сколько тревог, покадрово в `alarms_<tag>.csv` |
| `tools/eval_approach.py --tag v3` | дальность при подъезде: объект неподвижен в мире, поезд едет к нему |
| `tools/approach_trace.py --tag final` | тот же подъезд, но решение по каждому кадру: отсюда непрерывность тревоги |
| `tools/eval_fake_obj.py` | бэг организаторов: уровень по каждому из 10 объектов против эталона |
| `tools/eval_injection.py [--quick]` | синтетика: 8 фигур × 10 дальностей, доля найденных, ошибка дистанции |
| `tools/selflabel.py` | эпизоды СТОП, доказанно ложные проездом поезда через то же место |
| `tools/check_preproc.py`, `tools/input_report.py` | побитное совпадение C++ и Python, проверка входного потока |
| `tools/benchmark.py` | время разбора, пересчёта пути и проверки кадра |
| `tools/compare_row.py <тег> '<json>'` | строка сводной таблицы вариантов детектора (`compare_table.md`) |
| `tools/dashboard.py` | дашборд метрик одним файлом без сети: пять доказательств, 3D-кадр, таблица источников |
| `tools/demo.py` | демо-плеер одним файлом: детектор по кадрам записей в 3D |

Тесты ядра без записей: `docker compose --profile test up --build`.
